# Popup simulation refresh ownership

`popupVisualisationUpdater.ts` is the shared execution layer. Its semaphore serializes visualization execution for both queued and direct callers. It owns the abort controller, visibility/throttling checks, visualization construction, publication, and the publication generation guard. `popupSimulationRefreshQueue.ts` owns coalescing and supersession: the identity of each installed service pair, which requests are equivalent, which one is pending, and the invalidation merged across equivalent requests. The queue is an optional scheduling policy above the execution layer, not a replacement for it or a global ordering guarantee.

## Choosing an entry point

| Need | Entry point | Contract |
| --- | --- | --- |
| Explicit refresh that needs its completion outcome, such as rich settings, whose reply reports whether the refreshed simulation is available | `runPopupSimulationRefresh` in `popupSimulationRefreshQueue.ts` | Capture input and rich-count together; share equivalent requests, keep the latest pending request, carry invalidation forward, and settle each executed entry with its own outcome. Superseded queued requests return `status: 'superseded'`, not a failure. |
| Saved UI edits (account/network/mode changes, reset, removal, imports, time and gas edits) | `startPopupSimulationRefreshInBackground` | Capture input locally, invalidate stale results and publish updating state, then return. Background execution shares the queue, retains only the latest pending edit, reports errors, and prevents superseded results from publishing. |
| Complete-visualization requests, new-block updates, throttled editing, or existing flows that require an immediate refresh attempt | `updatePopupVisualisationIfNeeded` | Probe for an open consumer, optionally skip recent/unchanged work, and cancel obsolete cancellable execution. Returns the stored visualization, not a queued caller's success flag. |
| Bootstrap for an already-open consumer | `refreshPopupVisualisationForOpenConsumer` | Avoid another visibility probe; report unexpected errors and return the stored fallback so other bootstrap data can still load. |
| Explicit execution that must observe visualization errors | `updatePopupVisualisationState` | Execute under the same semaphore without visibility/throttling checks; `throwOnUnexpectedError` lets the caller report persistence failure explicitly. |

The direct paths deliberately retain their existing contracts. A block update must be able to cancel obsolete work promptly; bootstrap must not depend on a second open-consumer probe. Routing these paths through a latest-pending queue would change those guarantees.

Queue identity and supersession apply only among queue callers. Direct execution may run between queued entries or cancel their underlying cancellable execution. An executed queue entry returns `status: 'observed'` with the stored visualization's availability after its attempt. It does not attribute that state to a particular request or promise that it remains unchanged afterward. Superseded entries never report availability; callers must not interpret supersession as a simulation failure. All paths use the execution layer's serialization and storage/publication logic. Local invalidation advances a shared publication generation, so even direct bootstrap work started before an edit cannot store or broadcast obsolete results. The executor prepares requests that capture that generation before snapshot/preflight reads and checks it again inside the storage lock. `preparePopupVisualisationRefresh` in the updater returns a `PopupVisualisationRefreshRequest`: a plain-data `target` describing what the refresh would compute (visualization fingerprint, block hash, rich count, stack context and the generation it captured), or no target when it cannot be described, and an `execute` closure. Services, snapshot and the generation guard stay in that closure, so the queue cannot read or advance the generation or supply a publication predicate. The queue entry points turn it into a queued request with `toQueued`, which pairs a described target with a token for the service pair from `identify`, a registry each refresher created by `createPopupSimulationRefresher` keeps in its own closure; queued entries hold the token, never the services. The refresher treats two requests as equivalent only when their tokens match and their target descriptions are equal; a request without a target never joins other work. Invalidation is decided by the caller once and merged across equivalent requests by the queue, which passes it to `execute`; requests carry no invalidation of their own. Supersession prevents publication without suppressing unexpected-error reporting.

When adding a trigger, choose the required cancellation, visibility, error, and return-value contract from the table. Changes to visualization execution belong in `popupVisualisationUpdater.ts`; changes to interactive sharing/supersession belong in `popupSimulationRefreshQueue.ts`.

`captureSimulationSnapshot` reads the selected network, stack context, input and rich count at the storage boundary. Execution requires that snapshot; cache checks and execution share `getSimulationProviderForSnapshot`, which uses its network selection without re-reading global settings. Signer-only snapshots expose no simulation provider even though the service owner retains a supported provider for a later configured selection. The interactive queue carries the same snapshot through fingerprinting and execution. A missing RPC URL cannot be used to construct replacement RPC services.

Access approval schedules the account-change simulation refresh after publishing local invalidation, so the old account visualization cannot be approved as current. Permission persistence, provider notifications and the account request reply do not await remote simulation work. Other interactive settings transitions acknowledge committed state without awaiting their scheduled visualization refresh. Rich-setting edits, wallet network acknowledgements and Safe-owner validation remain awaited.

Imports acknowledge persisted stack changes after local invalidation, with visualization scheduled separately. Safe signature imports still validate current owners and signatures before persistence. Address-form validation reads local metadata; optional identification runs separately and preserves newer form edits.

Views consume each refresh through the `popup_simulation_state_changed` publication and render the state it carries. They must not answer it with `popup_requestCompleteVisualizedSimulation` or `popup_requestSimulationMetadata`: the metadata request simulates the current stack in simulation mode, and a complete-visualization request simulates and publishes again whenever the home popup or simulation stack page answers the open-consumer probe, so the views would keep triggering each other. Views receive the publication only through `subscribeToSimulationStatePublications` in `components/simulationStatePublications.ts`, which registers through the popup listener boundary so an error while handling it is reported as `popup_message_listener_failed`, and `test/tests/simulationStatePublicationConsumers.test.tsx` enforces the contract: it fails when other popup code handles the publication, when a view subscribes, directly or through `useLiveSimulationHomeData`, without being rendered by the test, or when a rendered view answers publications with either request. The background handlers stay unguarded because the same requests must still simulate when a view opens or its active stack changes. FetchSimulationStack sends both requests once when it opens. It does not answer the probe, so without one of those pages the stored visualization may predate the current stack; in simulation mode the metadata request simulates the current stack for its address references, and later finished publications replace them. A publication can arrive before those replies, so the page passes publications and both replies to `applySimulationStackUpdate` in `components/pages/fetchSimulationStackUpdates.ts`, the only writer of what it shows: the complete-visualization reply is ignored when `predatesVisualisation` finds it was stored before the displayed state (a lower simulation id, or the updating state of the refresh whose result is displayed), and the metadata reply only fills address references that no finished publication has supplied yet.

Updating and failed publications keep the previous state's address book entries (`retainPreviousVisualisation`) or, after a failed provider preparation, carry none, so they may not match the stack they describe. `utils/popupVisualisationLifecycle.ts` owns this rule and the order of stored states, and lives in `utils` so the background updater and popup views both depend on it without popup code importing from `background`: the updater builds those states with `retainPreviousVisualisation`, including the updating state that a scheduled UI edit publishes before its refresh runs (`publishPendingPopupVisualisation`), a view that shows address book entries separately from the rows asks `hasCurrentAddressBookEntries` whether a published state's entries replace the ones it shows, and `predatesVisualisation` orders two states by simulation id and, within one id, puts the updating state before the refresh's result. How a view combines its own replies with publications stays with that view.

External-wallet signing transitions do not enqueue simulation refreshes: wallet acknowledgment depends on applying the selected network, not RPC simulation availability. Simulation-mode transitions and selected Safe signing stacks schedule their visualization refreshes separately from command completion.

`updatePopupVisualisationIfNeeded` takes named options for invalidation, throttling, unchanged-input skipping, and a captured snapshot. Omitted options keep the normal direct-refresh behavior. The interactive queue supplies its captured snapshot and owns coalescing; the executor owns serialization.

Active settings commands receive `SimulationServicesOwner`, not a service pair captured before waiting for the transition semaphore. They read `getCurrent()` when preparing the refresh, so preceding network reconciliation supplies the installed services. Both popup and dapp RPC requests enter `changeActiveRpc` in `walletSwitch.ts`, which owns routing, shared Safe network restrictions, local promotion, and correlated wallet dispatch.

The intercepted-request pipeline also carries only the service owner. Provider callbacks obtain services when their work starts. Access admission, dialog callbacks, resolution, and permission persistence carry only the owner across user waits; replayed requests select the current services after approval. RPC execution captures one pair after admission and uses it for both lazy simulation preparation and RPC handling; permission persistence carries the owner into any subsequent prompts. An in-flight RPC does not switch providers halfway through execution.

## Popup handler service contracts

Choose the registration that describes the operation:

| Registration | Handler context | Boundary |
| --- | --- | --- |
| `popupMessageHandler` | Live service owner | Orchestration, settings transitions, opening/resolving prompts, or work that must follow the current selection after a wait. Pass the owner through the wait and obtain services when the next execution stage begins. |
| `popupSnapshotMessageHandler` | `PopupSnapshotContext.services`, without the owner or simulation-reset callback | One fixed-provider operation. The registry captures the pair at invocation, not registration; asynchronous work within that operation retains the same pair. A later invocation sees the newly installed pair. |

Transaction confirmation uses the owner registration and obtains services after refreshing wallet accounts. Visualization, metadata, and simulation operations use the snapshot registration where their existing execution contract requires a fixed pair. Do not use a snapshot registration to orchestrate a new user prompt or continue against a newly selected endpoint after that prompt; those stages need the owner contract.

`SimulationServicesOwner.ensureNetwork(selectedNetwork)` compares the selected chain and RPC URL with the installed network recorded by the owner. The injected-services constructor receives that initial network explicitly, and reconciliation advances it only after replacement succeeds; fake clients therefore do not need to override `getRpcEntry()`. A configured endpoint that differs replaces the service pair and returns `replaced`; a matching endpoint or a metadata-only selection returns `unchanged`. A signer-only selection returns `signerOnly` and retains the fallback services, which cannot be used for simulation. RPC-list edits pass `{ updateMetadata: true }` so changed names, currency details, and explorer metadata also replace the pair without mutating captured clients. List preferences alone do not require replacement. Replacement stops the old client's background polling. Active-settings transitions use the outcome, together with stack-context changes, to decide whether to refresh; signer-only outcomes refresh any active simulation or Safe stack to reflect unavailable simulation. RPC-list updates use the same admitted, serialized transition and refresh rule as other settings commands; the editor and background handler share `resolveRpcNetworkAfterListChange`, which reconciles only selections present in the previous list and prefers exact identity, then newly edited metadata for the same endpoint, then an existing endpoint alias, then the chain primary or first remaining entry. Imported/custom selections absent from the previous list and signer-only selections remain unchanged by unrelated list edits. Explicit endpoint edits select the replacement before saving the list; same-endpoint metadata edits use list reconciliation while the original selection still identifies its entry.

`EthereumClientService.cleanup()` does not destroy its request handler, clear its endpoint, or invalidate RPC methods: an already-started snapshot can still finish against its original provider. A snapshot is therefore a fixed endpoint, not a promise to represent the latest selection. It must not be reused for a later independent operation. The registry types make that choice visible and prevent snapshot handlers from calling owner-based lifecycle APIs through their context.

Website-access handlers run the `applyWebsiteAccessUpdate` workflow (persist, reload, reconcile) and address-book edits reconcile directly; both await `reconcileCommittedWebsiteAccessOrFailClosed` for committed permissions and request-blocking rules, which fails closed by clearing every approval and rethrows, then call `startWebsiteAccessUiUpdateInBackground` for prompts and icons, also when an earlier workflow step failed. Active-settings transitions await `reconcileWebsiteApprovalAccesses`, which reports failures and continues, under the settings lock, then start the same background UI update. `updateWebsiteApprovalAccesses` awaits reconciliation and the prompt and icon work and reports failures of both; it is for flows that must finish prompting before continuing, not for local commands. None of these takes an error-handling flag: the function name states whether it awaits and whether it fails closed or reports. The background task supervisor owns scheduled UI follow-ups, exposes pending task context and completion outcomes, and attributes durable error reports to their initiating operation. Tests await the same supervisor without mocking execution. Gas-limit edits publish changed pending requests immediately after local invalidation, using the stored visualization rather than waiting for a simulation; stack-only edits do not broadcast an empty confirmation list. Every confirmation-dialog update, from gas edits, metadata refreshes and `updateConfirmTransactionView`, goes through `publishConfirmTransactionDialogPendingTransactions` in `windows/confirmTransaction.ts`, which sends the pending-requests message together with its companion `popup_update_confirm_transaction_dialog` message and sends nothing for an empty queue. The dialog state those messages carry comes from `buildConfirmTransactionDialogState` in the same module, which owns the simulation-mode/passthrough rule (by the active settings' mode, or by the request's own mode for metadata refreshes), the RPC status read and the block number source: the view update and metadata refreshes fetch the block number from the node, as on main, and only the gas edit uses the cached head. The UI and resolution boundary prevent approval with simulation results from the previous gas limit unless the user ticked send-anyway for the reviewed request. Confirmation refreshes claim ownership before asynchronous transaction construction and check it again before cancelling an earlier simulation, so obsolete construction cannot cancel the latest gas edit. Metadata enrichment runs outside the visualization storage lock and commits only onto the visualization it read: `getPopupVisualisationStateWithRevision` returns the stored visualization with a revision that `updatePopupVisualisationWithCallBack`, the only writer, advances on every committed write, even one that stores an equal state, and `updateSimulationMetadata` commits only if the revision is unchanged inside the lock. Remote lookups therefore cannot delay local invalidation or overwrite newer progress/results. The revision lives in memory, because a reader compares it within one background lifetime and a restart discards both. Confirmation runs keep their own guards (see below).

## Confirmation dialog staleness

A pending transaction confirmation stores one simulation run, and three kinds of guard keep an older result from replacing a newer one. Each answers a different question, so none can stand in for another:

| Guard | Where | Question | Why it is not one of the others |
| --- | --- | --- | --- |
| Simulation timestamps: `simulationStartedTimestamp`, compared by `shouldReplacePopupVisualisation` when a new confirmation stores its first simulation; `simulationConductedTimestamp`, compared by `refreshPopupConfirmTransactionSimulation` when a refreshed simulation is stored | `windows/confirmTransaction.ts`, `popupMessageHandlers.ts` | Did this simulation start, or run, before the one already stored? | Both are stored in whole seconds, so two runs in the same second tie. |
| `confirmationRunId` from `getNextConfirmationRunId` | `confirmTransactionSimulation.ts` | Is the stored run still the run this metadata refresh read? `refreshPopupConfirmTransactionMetadata` compares it for equality before writing (`isSameConfirmationRun`). | Overlapping metadata refreshes read the same run and share its id. |
| `latestConfirmationMetadataRefresh` | `popupMessageHandlers.ts` | Is this the latest started metadata refresh? Only that one stores and sends its lookups. | It counts metadata refreshes, not runs: storing a new run does not change it. |

A run id is the random id of the background lifetime that ran the simulation (`lifetime`) and the run's place among that lifetime's runs (`sequence`). It is stored with the run and compared only for equality, so unlike the popup refresh generation (`popupRefreshGeneration.ts`) neither part needs a persisted counter. The sequence starts over after a restart, but the lifetime doesn't repeat, so a new run never gets the id of a run stored before the restart. A metadata refresh that read a stored run therefore writes only onto that run, whichever background lifetime stored it, and its own re-stamped `simulationConductedTimestamp` or names don't change the answer, because the run's content is not part of its identity. A confirmation stored without a run id decodes as a run of no lifetime, which no new run matches. The metadata refresh counter lives in memory because a refresh never outlives the background. #1647 uses the same `{ lifetime, sequence }` id, and #1622, #1633 and #1651 still use a numeric `confirmationRunId` that has to move to it when they merge.

The confirmation popup tags displayed requests with a local `source` discriminant: `storage` for its initial paint and `background` for validated bootstrap or push copies. Only the latter carries a `reviewedResultId` that an accept returns unchanged; consumers must narrow the source before using it. The tag stays in popup state and is never persisted or sent over the wire. One bounded bootstrap loop fetches the confirmable copy.
