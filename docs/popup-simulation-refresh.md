# Popup simulation refresh ownership

`popupVisualisationUpdater.ts` is the shared execution layer. Its semaphore serializes visualization execution for both queued and direct callers. It owns the abort controller, visibility/throttling checks, visualization construction, and publication. The queue is an optional scheduling policy above this layer, not a replacement for it or a global ordering guarantee.

## Choosing an entry point

| Need | Entry point | Contract |
| --- | --- | --- |
| Interactive settings changes, reset, or explicit refresh | `queuePopupSimulationRefresh` in `popupSimulationRefreshQueue.ts` | Capture input and rich-count together; share equivalent revisions, keep the latest pending request, carry invalidation forward, and settle each executed entry with its own outcome. Superseded queued requests return `status: 'superseded'`, not a failure. Reset forces invalidation after clearing the stack. |
| Complete-visualization requests, new-block updates, throttled editing, or existing flows that require an immediate refresh attempt | `updatePopupVisualisationIfNeeded` | Probe for an open consumer, optionally skip recent/unchanged work, and cancel obsolete cancellable execution. Returns the stored visualization, not a queued caller's success flag. |
| Metadata-only change (address-book or ENS edit) | `publishAddressBookChangeAndRelabelSimulations` in `addressBookChangePublication.ts` | Broadcast the change at once, then re-label the stored stack and displayed confirmation in the background without simulating; see [Address-book re-labels](#address-book-re-labels). |
| Import/persistence that must observe visualization errors | `updatePopupVisualisationState` | Execute under the same semaphore without visibility/throttling checks; `throwOnUnexpectedError` lets the caller report persistence failure explicitly. |

The direct paths deliberately retain their existing contracts. A block update must be able to cancel obsolete work promptly; an import cannot silently become a superseded queue entry; a metadata refresh must not depend on an open-consumer probe or start a simulation. Routing these paths through a latest-pending queue would change those guarantees.

Queue identity and supersession apply only among queue callers. Direct execution may run between queued entries or cancel their underlying cancellable execution. An executed queue entry returns `status: 'observed'` with the stored visualization's availability after its attempt. It does not attribute that state to a particular request or promise that it remains unchanged afterward. Superseded entries never report availability; callers must not interpret supersession as a simulation failure. All stack paths use the execution layer's serialization and storage logic; the confirmation re-label instead runs on its own semaphore and writes through the pending-confirmation storage. All paths except the metadata re-labels also publish `popup_simulation_state_changed`; the re-labels announce themselves with `popup_simulationsRelabelled` instead.

When adding a trigger, choose the required cancellation, visibility, error, and return-value contract from the table. Changes to visualization execution belong in `popupVisualisationUpdater.ts`; changes to interactive sharing/supersession belong in `popupSimulationRefreshQueue.ts`.

`captureSimulationSnapshot` reads the selected network, stack context, input and rich count at the storage boundary. Execution requires that snapshot; cache checks and execution share `getSimulationProviderForSnapshot`, which uses its network selection without re-reading global settings. Signer-only snapshots expose no simulation provider even though the service owner retains a supported provider for a later configured selection. The interactive queue carries the same snapshot through fingerprinting and execution. A missing RPC URL cannot be used to construct replacement RPC services.

External-wallet signing transitions do not enqueue simulation refreshes: wallet acknowledgment depends on applying the selected network, not RPC simulation availability. Simulation-mode transitions and selected Safe signing stacks retain their visualization refreshes.

`updatePopupVisualisationIfNeeded` takes named options for invalidation, throttling, unchanged-input skipping, and a captured snapshot. Omitted options keep the normal direct-refresh behavior. The interactive queue supplies its captured snapshot and owns coalescing; the executor owns serialization.

Active settings commands receive `SimulationServicesOwner`, not a service pair captured before waiting for the transition semaphore. They read `getCurrent()` when preparing the refresh, so a preceding endpoint reset supplies the installed services. Both popup and dapp RPC requests enter `changeActiveRpc` in `walletSwitch.ts`, which owns routing, shared Safe network restrictions, local promotion, and correlated wallet dispatch.

The intercepted-request pipeline also carries only the service owner. Provider callbacks obtain services when their work starts. Access admission, dialog callbacks, resolution, and permission persistence carry only the owner across user waits; replayed requests select the current services after approval. RPC execution captures one pair after admission and uses it for both lazy simulation preparation and RPC handling; permission persistence carries the owner into any subsequent prompts. An in-flight RPC does not switch providers halfway through execution.

## Address-book re-labels

Address-book and ENS edits change only names, ABIs and token metadata, so `publishAddressBookChangeAndRelabelSimulations` re-labels the stored simulations instead of simulating again.

- **Callers:** the popup handlers that save or remove address-book entries, change a Safe simulation signer or set an ENS name, watch-asset approval, and a successful settings import (`popup_import_settings`), which publishes the imported address book once the imported settings are applied. The startup migration does not publish: it runs before the simulation services exist and only converts stored entries to the current format. Neither do the ENS and metadata caching done during lookups.
- **Messages:** `popup_addressBookEntriesChanged` is broadcast at once, as before, so replies, locks and views that list address-book data never wait for simulation work. `popup_simulationsRelabelled` follows once both re-labels settle, also when there was nothing to re-label or a re-label failed and was reported. Only simulation views handle it, the same way as `popup_addressBookEntriesChanged`: the home popup and stack page re-read cached home data once their first fresh home data has arrived, and before that they request fresh home data, the refresh they need anyway because they show no simulation yet and discard cached replies until the first fresh one; the confirmation dialog re-reads its stored state through `popup_refreshConfirmTransactionMetadata`. Every sender of the dialog's pending confirmations and stack, `updateConfirmTransactionView` and these refreshes alike, reads them from storage and sends them through `sendStoredStateToConfirmTransactionDialog` in `confirmTransaction.ts`, one at a time, so the update the dialog applies last carries the latest stored state. Like the re-label, this dialog refresh makes no RPC request, so the dialog gets the new names also while the node is unreachable: it sends a metadata update, `popup_update_confirm_transaction_dialog_metadata` (`sendMetadataUpdateToConfirmTransactionDialog`), with the pending confirmations and stack only, and the dialog applies them without touching the block number and connection status it shows. The messages that do carry a block number, `updateConfirmTransactionView`'s updates, the bootstrap reply and the RPC status messages, give the node's latest block as their sender knows it, so the dialog's block has one meaning. A displayed signable message is visualised again for a metadata update only, naming its addresses as the re-label does from the entries its first visualisation recorded (the pending message's `identifiedAddressBookEntries`); a message stored without that record keeps its stored visualisation. Such refreshes run one at a time on their own lock, not the dialog's, so of their updates the one sent last read the newest address book. The cached home data the home popup and stack page request needs no RPC request either; only a view that has not received its first fresh home data yet refreshes through the node, as it does on mount. The re-label itself never starts a simulation or publishes `popup_simulation_state_changed`, which FetchSimulationStack answers by requesting new simulations.
- **No open view needed:** re-labels run whether or not a view is open, because bootstraps and later readers serve stored results without simulating while their input is unchanged.
- **No RPC request (`visualizeStoredRunWithoutNode` in `storedRunVisualisation.ts`):** a re-label visualises the stored run again, so names, ABI-parsed input, token metadata and every protector warning follow the address book, but it makes no RPC request, so it neither simulates nor fails or keeps old names when the node is unreachable. A simulation run makes the same visualisation's lookups on the node (`visualizeSimulatorState` in `simulationUpdating.ts`, which keeps only live node-backed simulation); the re-label answers each one from local data and the stored run instead. Both build the one `VisualisationLookups` type, whose members are all required, and pass it to the same visualisation (`visualizeSimulatorStateWithLookups`), so a lookup added to it fails typecheck until both modes supply it:
  - Addresses (`lookUpMetadataForRelabel` in `metadataUtils.ts`): the current address book, then bundled metadata, then what the run's own address lookups resolved for the address, else the bare address. A simulation run records every entry its lookups resolve from the address book, bundled metadata or the chain (`recordIdentifiedAddresses`), including those for signed messages such as a Permit2 token, and stores them with the run as `identifiedAddressBookEntries`. A recorded entry the chain identified (`entrySource` `'OnChain'`) stands in as it is; a recorded user or bundled entry that is no longer known keeps only its token kind and decimals, under the bare address, so the run's token amounts and signed approvals still render. Entries are never parsed out of the stored visualisation, which carries website-controlled values such as typed-data messages. An address is never identified on chain, which would read its code and probe its token metadata with `eth_simulateV1`, so a removed user entry shows what the run identified or the bare address until the next simulation identifies it again. The bare address is marked `'OnChain'`, so like any address identified on chain it is flagged as not in the address book.
  - ENS names: only those stored locally; a name hash no lookup has resolved yet stays unnamed.
  - Senders' EIP-7702 delegations and token prices: those stored with the run, a price only while its token is still known with the same decimals.
  - Protector chain reads, whether an address has code where the transaction ran (a simulated read once another transaction runs before it) and the gas price: replayed from `protectorChainReads`, which each simulated transaction records when its run is visualised. Every chain read a protector makes goes through `ProtectorChainReads` for this reason: a protector is given only those reads, the address identification (`IdentifyAddress`, a plain function type in `types/metadataLookups.ts` with `MetadataLookups`) and the connected chain id as a plain value, never a client, and the visualisation itself gets the services' network as plain data, so its types keep the re-label from reaching the node.
  - Runs stored by older versions without recorded protector chain reads or `identifiedAddressBookEntries` are skipped until they are simulated again.
- **Stack (`relabelPopupVisualisation`):** runs under the execution semaphore with the shared abort controller captured at request time, so a newer block, stack or failure refresh cancels it, also while it is queued. It skips pending, invalidated, failed, empty and other-chain states. Re-labels do not count as running simulations, so `onlyIfNotAlreadyUpdating` callers still refresh while only a re-label holds the semaphore.
- **Displayed confirmation (`relabelDisplayedConfirmationSimulation` in `confirmationRelabel.ts`):** re-labels the stored run of the first pending transaction; `publishAddressBookChangeAndRelabelSimulations` requests it for every change, and again for a confirmation run in flight that the change made stale (below). Re-labels run one at a time, so the last one reads the latest address book. Nothing cancels them, not even a new simulation of the displayed request: the write guard keeps a re-label from replacing a run stored meanwhile, and a new run that stores nothing (aborted, or its RPC request failed) leaves the re-labelled run in place. Failed, unsimulated and other-chain runs, and runs stored without a `confirmationRunId` by older versions, are skipped.
- **Confirmation runs in flight (`confirmationRunStorage.ts`):** a confirmation run is stored by its caller after its name lookups, so the re-label that follows a change cannot reach a run that is still running, and before a request's first run is stored there is no run to re-label at all. Confirmation-run storage is its own module, which the confirmation window, Safe signer selection and the address-book re-label depend on; it knows nothing of address books. Every confirmation workflow that stores a run (the first run in `openConfirmTransactionDialogForTransaction`, the dialog's re-simulation in `refreshPopupConfirmTransactionSimulation`, and a direct Safe execution simulated again for a new signer in `refreshAndPersistSafeSignerSelection`) simulates and stores it through `simulateAndStoreConfirmationRun`, writing the run with the `storeRun` it hands out, the only writer of confirmation runs; `confirmTransactionSimulation.ts` only produces runs. `storeRun` reports whether the write stored a new run, one whose `confirmationRunId` differs from that of the run stored before, so no caller reports that itself. `simulateAndStoreConfirmationRun` keeps the run in flight from before its first lookup until it returns. The change itself is owned by the publish step: `publishAddressBookChangeAndRelabelSimulations` marks every run then in flight stale (`markConfirmationRunsInFlightStale`) before it awaits anything, handing it the displayed-confirmation re-label as its refresh, and a stale run that stored a new run requests that one more re-label before it returns, the same guarded and serialized re-label a change requests. The run itself is never repeated: a run marked by several changes keeps the first refresh, which runs after the run is stored and so reads every change, so it adds at most this one re-label to those the changes request themselves. A run that was aborted (it returns no run), a run whose write kept the stored run (a newer run is already stored, the request was resolved, or the write only recorded an approval error) and a run during which nothing was published request no re-label.
- **Writes:** the stack and confirmation re-labels, including the one a stored run requests, go through `relabelStoredSimulation` in `simulationRelabel.ts`, the only stale-write guard. It replaces only the metadata, keeping the simulation, its run id (the stack's `simulationId`, a confirmation's `confirmationRunId`), timestamps and approval status, and writes only while the same run (same run id) is stored and can still be re-labelled, because a stack invalidation can carry the id of the run it raced with. Each caller supplies how to read and write its stored result, which results can be re-labelled, the abort controller that newer work aborts (none for the confirmation re-label), and the serialization it runs under.
- **Known limitations:** pending confirmations behind the displayed one are not re-labelled, so a run of such a request that a change overlapped re-labels the displayed confirmation instead of its own. As before, signable messages are not re-labelled in storage either, so a later `updateConfirmTransactionView` sends the visualisation stored when the message arrived until the dialog refreshes its metadata again.

## Popup handler service contracts

Choose the registration that describes the operation:

| Registration | Handler context | Boundary |
| --- | --- | --- |
| `popupMessageHandler` | Live service owner | Orchestration, settings transitions, opening/resolving prompts, or work that must follow the current selection after a wait. Pass the owner through the wait and obtain services when the next execution stage begins. |
| `popupSnapshotMessageHandler` | `PopupSnapshotContext.services`, without the owner or reset callback | One fixed-provider operation. The registry captures the pair at invocation, not registration; asynchronous work within that operation retains the same pair. A later invocation sees the newly installed pair. |

Transaction confirmation uses the owner registration and obtains services after refreshing wallet accounts. Visualization, metadata, and simulation operations use the snapshot registration where their existing execution contract requires a fixed pair. Do not use a snapshot registration to orchestrate a new user prompt or continue against a newly selected endpoint after that prompt; those stages need the owner contract.

`SimulationServicesOwner.reset()` stops the replaced client's background polling and installs a new pair. `EthereumClientService.cleanup()` does not destroy its request handler, clear its endpoint, or invalidate RPC methods: an already-started snapshot can still finish against its original provider. A snapshot is therefore a fixed endpoint, not a promise to represent the latest selection. It must not be reused for a later independent operation. The registry types make that choice visible and prevent snapshot handlers from calling owner-based lifecycle APIs through their context.
