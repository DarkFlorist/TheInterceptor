# Popup simulation refresh ownership

`popupVisualisationUpdater.ts` is the shared execution layer. Its semaphore serializes visualization execution for queued, direct and confirmation callers. It owns the abort controller, visibility/throttling checks, visualization construction, and publication of the shared visualization, which follows the latest stack. The queue is an optional scheduling policy above this layer, not a replacement for it or a global ordering guarantee.

## Choosing an entry point

| Need | Entry point | Contract |
| --- | --- | --- |
| Interactive settings changes, reset, or explicit refresh | `queuePopupSimulationRefresh` in `popupSimulationRefreshQueue.ts` | Capture input and rich-count together; share equivalent revisions, keep the latest pending request, carry invalidation forward, and settle each executed entry with its own outcome. Superseded queued requests return `status: 'superseded'`, not a failure. Reset forces invalidation after clearing the stack. |
| Complete-visualization requests, new-block updates, throttled editing, or existing flows that require an immediate refresh attempt | `updatePopupVisualisationIfNeeded` | Probe for an open consumer, optionally skip recent/unchanged work, cancel obsolete cancellable execution, and store and broadcast the result as the shared visualization. Callers get the stored visualization, not a queued caller's success flag. |
| The interactive queue's refresh of the revision it computed | `updatePopupVisualisationForSnapshot` | The same guards, attempt and publication as `updatePopupVisualisationIfNeeded`, for a snapshot the caller supplies, without reusing a merely recent result. Returns that snapshot's visualization: the stored one only if it already describes the snapshot's input, otherwise the one built for it, or a content-free unavailable state if no refresh ran or it was superseded or failed. |
| Confirmation bootstrap, dialog updates and metadata refreshes | `computeConfirmationVisualisation` | The confirmation window is the consumer, so there is no visibility probe. Compute the visualization of the confirmation's own snapshot and return it; never store or broadcast it as the shared visualization, which a newer stack may have replaced. Shared refreshes cannot cancel it. Report unexpected errors and return the unavailable state, so the rest of the dialog still updates. |
| Import/persistence that must observe visualization errors | `updatePopupVisualisationState` | Execute under the same semaphore without visibility/throttling checks; `throwOnUnexpectedError` lets the caller report persistence failure explicitly. |

The direct paths deliberately retain their existing contracts. A block update must be able to cancel obsolete work promptly; an import cannot silently become a superseded queue entry; a confirmation must neither depend on an open-consumer probe nor replace the shared visualization with its own snapshot. Routing these paths through a latest-pending queue would change those guarantees.

Queue identity and supersession apply only among queue callers. Direct execution may run between queued entries or cancel their underlying cancellable execution. An executed queue entry returns `status: 'observed'` with the availability of the visualization its attempt produced for its snapshot. It does not promise that the stored state remains unchanged afterward. Superseded entries never report availability; callers must not interpret supersession as a simulation failure. All paths use the execution layer's serialization; only the shared refreshes store and publish.

When adding a trigger, choose the required cancellation, visibility, error, and return-value contract from the table. Changes to visualization execution belong in `popupVisualisationUpdater.ts`; changes to interactive sharing/supersession belong in `popupSimulationRefreshQueue.ts`.

Snapshots are built only under the network transition lock: `readNetworkSnapshot` and `readNetworkState` in `networkTransitionLock.ts` read the selected network, stack context, input and rich count at the storage boundary and stamp the committed network change generation in the same locked section. Execution requires that snapshot; cache checks and execution share `getSimulationProviderForSnapshot`, which uses its network selection without re-reading global settings. Signer-only snapshots expose no simulation provider even though the service owner retains a supported provider for a later configured selection. The interactive queue carries the same snapshot through fingerprinting and execution. A missing RPC URL cannot be used to construct replacement RPC services. A refresh whose services serve another endpoint than its snapshot's network, such as services captured just before a network change, neither simulates, cancels nor invalidates anything; the refresh that follows the change publishes that network's result. Every committed network change advances a generation under the network transition lock, and snapshots record the generation they were read at; a shared refresh without a snapshot of its own reads one under that lock before it waits for the visualisation semaphore. A shared refresh whose snapshot is older than the latest network change, including one that returned to the same endpoint, neither cancels another refresh, simulates, stores nor broadcasts; invalidating the stored result runs in the same serialized section as the refresh, so it cannot overwrite a newer network's completed result. Metadata enrichment of the stored visualisation runs only with a client of that visualisation's network and writes nothing once its snapshot's generation is no longer current. Stores of the shared visualisation evaluate the generation once they hold the storage update semaphore, so a write that waited for metadata enrichment while a network change committed is skipped. Fresh and cached home data updates broadcast the home page only while their snapshot's generation is current and otherwise start over, and a Gnosis Safe confirmation whose stack reconciliation removed executed operations re-reads the network and compares the same generation, so a return to the same endpoint or a signer-only network that keeps the client still counts as a network change.

Views consume each refresh through the `popup_simulation_state_changed` publication and render the state it carries. They must not answer it with `popup_requestCompleteVisualizedSimulation` or `popup_requestSimulationMetadata`: the metadata request simulates the current stack in simulation mode, and a complete-visualization request simulates and publishes again whenever the home popup or simulation stack page answers the open-consumer probe, so the views would keep triggering each other. Views receive the publication only through `subscribeToSimulationStatePublications` in `components/simulationStatePublications.ts`, which registers through the popup listener boundary so an error while handling it is reported as `popup_message_listener_failed`, and `test/tests/simulationStatePublicationConsumers.test.tsx` enforces the contract: it fails when other popup code handles the publication, when a view subscribes, directly or through `useLiveSimulationHomeData`, without being rendered by the test, or when a rendered view answers publications with either request. The background handlers stay unguarded because the same requests must still simulate when a view opens or its active stack changes. FetchSimulationStack sends both requests once when it opens. It does not answer the probe, so without one of those pages the stored visualization may predate the current stack; in simulation mode the metadata request simulates the current stack for its address references, and later finished publications replace them. A publication can arrive before those replies, so the page passes publications and both replies to `applySimulationStackUpdate` in `components/pages/fetchSimulationStackUpdates.ts`, the only writer of what it shows: the complete-visualization reply is ignored when `predatesVisualisation` finds it was stored before the displayed state (a lower simulation id, or the updating state of the refresh whose result is displayed), and the metadata reply only fills address references that no finished publication has supplied yet.

Updating and failed publications keep the previous state's address book entries (`retainPreviousVisualisation`) or, after a failed provider preparation, carry none, so they may not match the stack they describe. `utils/popupVisualisationLifecycle.ts` owns this rule and the order of stored states, and lives in `utils` so the background updater and popup views both depend on it without popup code importing from `background`: the updater builds those states with `retainPreviousVisualisation`, a view that shows address book entries separately from the rows asks `hasCurrentAddressBookEntries` whether a published state's entries replace the ones it shows, and `predatesVisualisation` orders two states by simulation id and, within one id, puts the updating state before the refresh's result. How a view combines its own replies with publications stays with that view.

External-wallet signing transitions do not enqueue simulation refreshes: wallet acknowledgment depends on applying the selected network, not RPC simulation availability. Simulation-mode transitions and selected Safe signing stacks retain their visualization refreshes.

`updatePopupVisualisationIfNeeded` takes named options for invalidation, throttling and unchanged-input skipping. Omitted options keep the normal direct-refresh behavior. The interactive queue passes its captured snapshot to `updatePopupVisualisationForSnapshot` and owns coalescing; the executor owns serialization.

Active settings commands receive `SimulationServicesOwner`, not a service pair captured before waiting for the transition semaphore. They read `getCurrent()` when preparing the refresh, so a preceding endpoint reset supplies the installed services. Both popup and dapp RPC requests enter `changeActiveRpc` in `walletSwitch.ts`, which owns routing, shared Safe network restrictions, local promotion, and correlated wallet dispatch.

The intercepted-request pipeline also carries only the service owner. Provider callbacks obtain services when their work starts. Access admission, dialog callbacks, resolution, and permission persistence carry only the owner across user waits; replayed requests select the current services after approval. RPC execution captures one pair after admission and uses it for both lazy simulation preparation and RPC handling; permission persistence carries the owner into any subsequent prompts. An in-flight RPC does not switch providers halfway through execution.

Ending a request must not depend on the simulation stack. Closing a confirmation window, startup recovery of orphaned requests, a reject action and a wallet's reply go through `resolvePendingRequestWithoutSnapshot`, which queues and delivers the website's reply first and reads a snapshot only for the view work after it. If that read fails, only the view is out of date.

## Popup handler service contracts

Choose the registration that describes the operation:

| Registration | Handler context | Boundary |
| --- | --- | --- |
| `popupMessageHandler` | Live service owner | Orchestration, settings transitions, opening/resolving prompts, or work that must follow the current selection after a wait. Pass the owner through the wait and obtain services when the next execution stage begins. |
| `popupSnapshotMessageHandler` | `PopupSnapshotContext.services`, without the owner or reset callback | One fixed-provider operation. The registry captures the pair at invocation, not registration; asynchronous work within that operation retains the same pair. A later invocation sees the newly installed pair. |

Transaction confirmation uses the owner registration and obtains services after refreshing wallet accounts. Visualization, metadata, and simulation operations use the snapshot registration where their existing execution contract requires a fixed pair. Do not use a snapshot registration to orchestrate a new user prompt or continue against a newly selected endpoint after that prompt; those stages need the owner contract.

`SimulationServicesOwner.reset()` stops the replaced client's background polling and installs a new pair. `EthereumClientService.cleanup()` does not destroy its request handler, clear its endpoint, or invalidate RPC methods: an already-started snapshot can still finish against its original provider. A snapshot is therefore a fixed endpoint, not a promise to represent the latest selection. It must not be reused for a later independent operation. The registry types make that choice visible and prevent snapshot handlers from calling owner-based lifecycle APIs through their context.
