# Dependency patches

`@noble/curves@2.2.0` is a direct build dependency because `build/vendor.mts` copies its root package into the extension. The same version satisfies `micro-eth-signer@0.19.0`; it is the sole installed curve-library version. Application and test code do not import Noble curve APIs directly.

`@noble/curves@2.2.0.patch` adds the locally defined `ERR_SECP256K1_INVALID_POINT` code at the existing secp256k1 non-residue and recovered-infinity errors. Point decoding preserves the square-root error as `cause`. TypeScript and distributed JavaScript agree; arithmetic is unchanged. This code is our patch contract, not an upstream Noble API.

`ethereumRecoveryBackend.ts` is the sole adapter for dependency-specific recovery behavior. It delegates to `micro-eth-signer`, translates the local code/cause metadata into a typed success/failure result, and propagates untagged exceptions. `ethereumSigning.ts` consumes that result without knowing the dependency tag or nesting. No human-readable diagnostics control recovery. The adapter also probes both invalid-point outcomes during module initialization in the shipped extension: an unpatched or incompatible backend fails immediately even when a custom build bypasses the preflight. It cannot silently turn a skipped authorization into an unexpected throw later in nonce accounting.

`check:recovery-dependency` resolves micro from the actual adapter module, then resolves Noble relative to that micro copy. It checks the micro and direct Noble pins, requires recovery and the root package copied by vendoring to resolve to the same real directory, verifies the patch declaration, and probes both invalid-point outcomes through that same adapter. The adapter and its import-free `runtimeTypeGuards.ts` dependency are intentionally environment-neutral shared modules: they must not acquire browser, extension or application-service imports. Build tooling imports this boundary to test the actual shipped implementation rather than a parallel build-only recovery path. Tests, typecheck and extension compilation run this guard before proceeding. The vendor implementation itself runs it before deleting or copying output, including when invoked directly. Hoisting is accepted when recovery and vendoring share the same package tree; a version, source-copy or tag mismatch fails before output is copied or a bundle is produced.

Bun applies the patch through `patchedDependencies` in `package.json` and `bun.lock`; Docker copies it before the frozen install. For every micro or Noble upgrade: inspect the upstream recovery and point-decoding changes, explicitly rebase/remove the patch in both TypeScript and distributed JavaScript, update the exact pins and frozen lockfile, then run the guard, recovery/nonce tests and required repository validation. Retain the runtime probes unless the adapter uses an upstream typed invalid-point result. Both build preflight and adapter initialization enforce the behavior before it can be used. The invalid-point tests enforce the tags; an oversized-input test enforces propagation of untagged library failures.
